# Exam Seat & Hall Allocation System — FastAPI Backend

Backend API for generating exam seat numbers and hall allocations for
ND1 / ND2 / HND1 / HND2 students, with two user types: **admin** and
**student**. Built with FastAPI + SQLAlchemy + JWT auth. SQLite by default
(zero setup); swap in Postgres/MySQL by changing one env var.

## 1. Setup

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env            # then edit SECRET_KEY etc.

python seed.py                  # creates the first superadmin account
uvicorn app.main:app --reload
```

Open **http://127.0.0.1:8000/docs** for interactive Swagger docs (every
endpoint below is listed there with a "Try it out" button).

Default seeded admin login (change immediately): `admin` / `ChangeMe123!`
(from `.env`).

## 1b. Run with Docker (local)

```bash
docker compose up --build
```

Serves the API at **http://localhost:8000**, running the same `seed.py` bootstrap on
every boot (idempotent - does nothing if the admin already exists) and persisting the
SQLite file in a named Docker volume so data survives rebuilds. Override any setting
with an `.env` file in this folder (docker-compose reads `SECRET_KEY`,
`ALLOWED_ORIGINS`, `DEFAULT_ADMIN_*` from your shell/`.env`).

Or build/run the image directly:

```bash
docker build -t exam-hall-allocator .
docker run -p 8000:8000 -v exam_data:/data \
  -e SECRET_KEY=some-long-random-string \
  -e ALLOWED_ORIGINS=http://localhost:5173 \
  exam-hall-allocator
```

## 2. Deploying to Render (backend)

This repo includes a `render.yaml` Blueprint, so the fastest path is:

1. Push this backend folder to a Git repo.
2. In the Render dashboard: **New → Blueprint**, point it at the repo. Render reads
   `render.yaml` and provisions a Docker web service plus a **1 GB persistent disk**
   mounted at `/data` - this is what makes SQLite survive deploys and restarts on
   Render's otherwise-ephemeral filesystem.
3. Before (or right after) the first deploy, edit these env vars in the Render
   dashboard for the new service:
   - `ALLOWED_ORIGINS` → your Vercel frontend URL, e.g. `https://your-app.vercel.app`
     (comma-separate multiple origins if needed).
   - `DEFAULT_ADMIN_PASSWORD` → set something private before the first boot (the
     container runs `seed.py` on every start, which only creates the admin if it
     doesn't exist yet - so changing this after the first successful boot has no
     effect; change the password from inside the app instead at that point).
   - `SECRET_KEY` is auto-generated by the blueprint (`generateValue: true`) - leave it.
4. Deploy. Render builds the `Dockerfile`, mounts the disk at `/data`, and
   `DATABASE_URL=sqlite:////data/exam_allocation.db` (already set in `render.yaml`)
   points SQLite at that disk.
5. Health check: Render pings `/` (see `healthCheckPath` in `render.yaml`), which
   returns `{"status": "ok", ...}`.

No Blueprint? You can also create the Web Service manually (**New → Web Service**,
choose **Docker** as the runtime, point at this repo) - just remember to add a
**persistent disk** mounted at `/data` yourself (Render dashboard → your service →
Disks), otherwise the SQLite file is wiped on every deploy/restart.

### Pairing with the Vercel frontend

The companion `exam-hall-frontend` (React + Vite) reads the backend URL from a single
`VITE_API_URL` environment variable. Once this backend is live on Render:

1. Copy its URL (e.g. `https://exam-hall-allocator-api.onrender.com`).
2. Set it as `VITE_API_URL` in the frontend's Vercel project settings and redeploy.
3. Come back here and set `ALLOWED_ORIGINS` to the frontend's Vercel URL (step 3
   above) so the browser's CORS check passes.

## 2. Domain model

| Concept | What it represents |
|---|---|
| `Department` | e.g. Computer Science, Statistics |
| `AcademicSession` | e.g. "2025/2026" |
| `Semester` | First/Second, belongs to a session, has status `draft` → `active` → `submitted` |
| `Course` | code + title (e.g. `COM211`) |
| `CourseOffering` | links a `Course` to a `Department` + `Level` + `Semester` — this is how admin "adds a course for a level/semester" and "links courses to a department" in one step |
| `Hall` | physical exam hall + total seat capacity |
| `ExamSchedule` | the timetable entry for a `CourseOffering`: date, start/end time, status (`scheduled`/`completed`/`cancelled`) |
| `HallAllocation` | assigns a `Hall` to an `ExamSchedule` (an exam can use several halls) |
| `HallDepartmentRange` | within a `HallAllocation`, reserves seats `[seat_start_no..seat_end_no]` for students of a `Department`+`Level` whose matric number falls in `[matric_start..matric_end]` — this is how you **mix two or more departments in one hall** |
| `Student` | self-registered: full name, matric no, department, level, semester |
| `StudentCourseAllocation` | auto-computed: every `CourseOffering` matching the student's department+level+semester |
| `SeatAllocation` | computed (student, exam) → (hall, seat number), derived from `HallDepartmentRange` |

## 3. Typical admin workflow

1. **Auth**: `POST /auth/register` (only works once, to create the first
   superadmin — after that use `/auth/register-additional` with a
   superadmin token). `POST /auth/login` (OAuth2 form: `username`,
   `password`) → returns a bearer token. Send it as
   `Authorization: Bearer <token>` on every admin call below.
2. **Departments**: `POST /departments` — `{"name": "Computer Science", "code": "CSD"}`
3. **Academic session & semester**:
   - `POST /sessions` — `{"name": "2025/2026"}`
   - `POST /semesters` — `{"session_id": 1, "name": "First"}` (created as `draft`)
   - `POST /semesters/{id}/start` — flips it to `active` (auto-closes any other active semester). Only an active semester accepts student registration.
4. **Courses & course offerings** (this is "add course for each level/semester" + "link course to department"):
   - `POST /course-offerings` —
     ```json
     {
       "course_code": "COM211",
       "course_title": "Data Structures",
       "course_unit": 3,
       "department_id": 1,
       "level": "ND2",
       "semester_id": 1
     }
     ```
   - Repeat per department/level/semester. An existing course can be re-linked to another department by passing its `course_id` instead of `course_code`/`course_title`.
5. **Halls**: `POST /halls` — `{"name": "Hall A", "code": "HA", "total_seats": 200, "rows": 20, "columns": 10}`
6. **Exam timetable** ("set exam date and time like a timetable"):
   - `POST /exams` — `{"course_offering_id": 1, "exam_date": "2026-11-10", "start_time": "09:00:00", "end_time": "11:00:00"}`
7. **Hall allocation** ("allocate hall for the exam", "mix two or more departments and matric number ranges"): a `HallAllocation` is one hall booked for one physical *sitting* (a date + start/end time); each `department_ranges` entry is a seat block for one department+level, sitting a specific `exam_schedule_id` (its own course) — this is how two departments writing two *different* courses at the same time end up sharing one hall, each seated in their own block:
   - `POST /hall-allocations` —
     ```json
     {
       "hall_id": 1,
       "department_ranges": [
         {"exam_schedule_id": 1, "department_id": 1, "level": "ND2", "matric_start": "CSD/ND/24/001", "matric_end": "CSD/ND/24/060", "seat_start_no": 1, "seat_end_no": 60},
         {"exam_schedule_id": 2, "department_id": 2, "level": "ND2", "matric_start": "STA/ND/24/001", "matric_end": "STA/ND/24/040", "seat_start_no": 61, "seat_end_no": 100}
       ]
     }
     ```
     All `exam_schedule_id`s in one call must share the exact same `exam_date`/`start_time`/`end_time` (they're in the same room at once). Calling this again for the same hall+sitting appends more department blocks to the existing booking instead of erroring, so you can build up a mixed hall over several calls.
   - This immediately (re)computes every matching, registered student's seat number for each affected exam. Call `POST /hall-allocations/exam/{exam_id}/recompute-seats` any time later (e.g. after more students register) — it reports `overflow_students` if a range runs out of seats. `DELETE /hall-allocations/department-ranges/{range_id}` removes just one block; `DELETE /hall-allocations/{id}` removes the whole hall booking.
   - **Automatic allocation (no hall/ranges/seat numbers to type):** `POST /hall-allocations/auto` —
     ```json
     {"semester_id": 1, "allow_mixing": true, "replace_existing": true, "dry_run": false}
     ```
     Pass `semester_id` (every exam in it) and/or `exam_ids`. The server groups exams into sittings (same date + start + end), then for each sitting seats the biggest exams first: each exam's registered students (department + level, ordered by matric number) are poured into free seat blocks — one hall when they all fit (smallest block that fits), otherwise the largest blocks first, splitting the matric order into consecutive ranges. With `allow_mixing: true`, leftover seats in a hall go to other departments sitting at the same time; with `false`, each hall holds one exam. Optional `hall_ids` limits which halls may be used. Halls booked for a *different overlapping* sitting are skipped, and seats held by exams outside the request are never touched. `replace_existing: true` redoes exams that already have a hall allocation (`false` skips them). `dry_run: true` returns the plan without saving anything. The response lists, per exam, the blocks created (hall, seat range, matric range), how many were seated, and any `unseated` matric numbers plus `warnings` (e.g. not enough total seats). Per-student seats are computed immediately. **Re-run it after late registrations** — it only plans for students who have registered by then.
8. **Mark an exam done**: `PATCH /exams/{id}/status` — `{"status": "completed"}`. This is instantly visible on the student's `/students/me/seats` and `/students/me/timetable`.
9. **Close the semester**: `POST /semesters/{id}/submit` — once submitted, students can no longer register for it or fetch seat allocations under it (`/students/me/seats` returns HTTP 403).

## 4. Typical student workflow

1. `GET /departments`, `GET /semesters/active` — populate the registration form.
2. `POST /students/register` —
   ```json
   {
     "full_name": "Adeola Grace Okon",
     "matric_no": "CSD/ND/24/015",
     "department_id": 1,
     "level": "ND2",
     "semester_id": 1
   }
   ```
   Returns a student bearer token + profile. Courses are auto-allocated
   from `CourseOffering` behind the scenes.
3. `GET /students/me/courses` — the auto-allocated course list.
4. `GET /students/me/seats` — seat number + hall name for every exam that
   has a hall allocated so far.
5. `GET /students/me/timetable` — the full personalized timetable (every
   registered course, with date/time/hall/seat once available, and exam
   status) — this is what the frontend renders/exports as a printable PDF.
6. Returning student without the original token: `POST /students/login` —
   `{"matric_no": "...", "full_name": "..."}` re-issues a token.

## 5. Notes on design choices

- **No password for students.** Registration doubles as "login" (matches
  the "student registers to access seat/hall" requirement); a lightweight
  JWT is still issued so subsequent calls are authenticated without
  resending full name + matric number every time.
- **Matric ranges are string/lexicographic**, so formats like
  `CSD/ND/24/001`..`CSD/ND/24/060` work as long as the numeric segment is
  zero-padded consistently. If your matric numbers aren't zero-padded,
  pad them at registration time on the frontend, or extend
  `services/allocation.py::_matric_in_range` with custom parsing.
- **Seat numbers are assigned by rank**, not by arithmetic offset from the
  matric number — every student in a department+level+matric-range block
  who actually registered is sorted by matric number and given
  consecutive seats starting at `seat_start_no`. This tolerates gaps
  (e.g. a student who never registers doesn't leave a hole).
- **Overflow handling**: if more students fall in a range than seats
  reserved for it, the extras are left unseated and reported back
  (`overflow_students`) rather than silently overwriting another block —
  the admin then widens the range or adds another hall/block.
- **Migrations**: `Base.metadata.create_all()` is used for simplicity. For
  a real deployment, switch to Alembic migrations instead.
- **CORS** is wide open (`allow_origins=["*"]`) for development — restrict
  it to your frontend's origin in production.
